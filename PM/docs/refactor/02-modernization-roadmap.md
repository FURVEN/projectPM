## 2. 남아 있는 레거시 리스크

1. **git 히스토리의 비밀값** — 과거 커밋에 DB 비밀번호·AES 키·Gmail 앱 비밀번호가 남아 있다. **값 교체(rotate)가 유일한 안전한 해결책**이다. (히스토리 재작성은 포크/클론과 충돌 위험)
2. **평문 비밀번호 비교 가능성** — `emp.checkLogin` 이 `pwd = #{pwd}` 로 직접 비교한다. DB에 평문 저장이라면 심각한 취약점. 해싱 도입은 데이터 마이그레이션이 필요해 이번 패스 범위 밖 (아래 4단계).
3. **테스트 커버리지** — 로그인 외 9개 모듈(전자결재, 근태, 휴가 등)은 여전히 무테스트.
4. **org.json 수동 직렬화** — 컨트롤러 8곳에 남아 있음. 응답 계약이 암묵적이라 리팩토링 취약.
5. **DB 스키마 부재** — 저장소에 스키마/시드 SQL 이 없어 신규 환경 구축이 불가능하다.
6. **런타임 검증 부재** — 이 리팩토링 환경에는 Oracle 이 없어 톰캣 기동+로그인 E2E 는 미검증. 단위 테스트와 컴파일/패키징으로만 검증했다.
7. 퇴역 스택: tomcat7-maven-plugin, JSP/Tiles, javax 네임스페이스, Java 8.

## 3. 권장 다음 단계 (순서 중요)

1. **Spring MVC 안정화** — Spring 5.3.22 → 5.3.39(최종 5.3.x) 패치 업그레이드 + 실제 톰캣에서 스모크 테스트. 프레임워크 교체 전에 현재 스택을 최신 패치로.
2. **외부 설정/프로파일 정리** — dev/prod 프로퍼티 분리, 로그 레벨 프로파일화, 파일 업로드 경로 등 남은 환경 종속값 외부화.
3. **테스트 커버리지 확장** — 모듈별 서비스/컨트롤러 단위 테스트, H2 + MyBatis 로 매퍼 SQL 검증(Oracle 방언 주의), MockMvc 도입.
4. **DB 마이그레이션 전략** — 스키마 덤프를 `PM/docs/sql/` 로 관리, Flyway/Liquibase 도입, **비밀번호 해싱(BCrypt) 마이그레이션** 계획 수립.
5. **API 경계 추출** — 컨트롤러의 org.json/Gson 수동 직렬화를 Jackson DTO 로 통일, 화면용 컨트롤러와 AJAX API 분리. 이 경계가 이후 프론트엔드 현대화(SPA)와 Boot 전환의 이음새가 된다.
6. **(선택) Spring Boot 마이그레이션** — 위 1~5가 끝난 뒤: web.xml → Boot 부트스트랩, XML → JavaConfig, 내장 톰캣. `*.pm` 패턴은 Boot 에서도 서블릿 매핑으로 유지 가능.
7. **(선택) Docker 화** — Oracle XE 컨테이너 + 앱 컨테이너 compose 로 개발환경 표준화.
8. **(선택) CI/CD** — GitHub Actions 로 `mvn verify` 게이트, 이후 배포 파이프라인.

## 4. 왜 Spring Boot 를 먼저 하지 않는가

- Boot 전환은 **부트스트랩(web.xml), 설정(XML), 뷰(JSP/Tiles), 내장 서버**를 동시에 건드리는 대형 변경이다. 회귀를 감지할 테스트가 없는 상태에서 하면 "옮겼지만 어디가 깨졌는지 모르는" 상태가 된다.
- JSP + Tiles 는 내장 톰캣(특히 jar 패키징)에서 제약이 많아, 뷰 전략 결정이 선행되어야 한다.
- 비밀정보 하드코딩·빌드 재현성·테스트 부재는 Boot 로 옮겨도 그대로 따라가는 문제다. **프레임워크가 아니라 위생이 먼저다.**
- 이번 패스가 만든 것(외부화된 설정, 상수화된 세션 계약, 계층별 단위 테스트)이 바로 Boot 전환 시의 안전망이 된다.

## 5. 포트폴리오 관점: 이 프로젝트를 소개하는 법

이 저장소는 "레거시를 Boot 로 다시 짰다"가 아니라 **"운영 중단 없이 레거시를 단계적으로 안정화했다"** 는 스토리로 소개하는 것이 좋다. 실무 레거시 현대화에서 실제로 요구되는 순서이기 때문이다.

면접/README 에서 강조할 포인트:

1. **진단 → 계획 → 실행 → 검증의 궤적이 커밋 로그로 남아 있다** (작은 커밋 + 문서 3종).
2. **동작 보존 제약 하의 리팩토링** — URL/AJAX 응답 형태/DB 스키마를 계약으로 취급하고, 그 계약을 테스트로 고정한 뒤 내부를 바꿨다.
3. **보안 개선의 현실적 처리** — 비밀값 외부화 + "히스토리에 남은 키는 rotate 필요" 를 문서화 (히스토리 재작성의 함정 인지).
4. **증거 기반 의존성 정리** — "안 쓰는 것 같아서" 가 아니라 저장소 전수 검색으로 증명 후 제거, 겉보기와 다른 것(commons-fileupload)은 이유와 함께 보존.
5. **빌드 재현성 확보** — 서드파티 저장소 단일 장애점 제거.
6. **하지 않은 것의 목록** — 범위 통제와 리스크 인지를 보여주는 가장 좋은 증거.
